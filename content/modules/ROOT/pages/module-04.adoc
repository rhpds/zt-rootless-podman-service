= A System Service

The service you have been managing is yours: started with `--user`, run by your manager, tied to your session. The same five declarations make it a system service — the kind the machine runs, like every other service on it: up at boot with no session, in the same journal as everything else, tied to nobody's login. A system service needs one thing the declaration is still missing: the boot wiring that pulls it in when the machine starts. In this module you will declare it, then move the completed files one directory over — where the system's manager runs them.

== One Directory Over

The application needs to come up at boot, and the wiring that pulls it in is declared, like everything else — one section in the declaration itself. The declaration lives in your project directory — that is where every change to it happens. Append the section the declaration is missing:

[source,bash,role=execute]
----
cat >> ~/webapp-quadlet/webapp.pod <<'EOF'

[Install]
WantedBy=default.target
EOF
----

Everything in this lab has been a user service: five files in your home directory, run by your manager, tied to your session. The same five files, complete with their boot wiring, make the application a system service — from `/etc/containers/systemd/`, under the system's manager, the way every other service on the machine runs.

The install — the same command, run as root:

[source,bash,role=execute]
----
sudo podman quadlet install ~/webapp-quadlet/
----

[source,text]
----
/etc/containers/systemd/webapp/store.container
/etc/containers/systemd/webapp/store.volume
/etc/containers/systemd/webapp/web.container
/etc/containers/systemd/webapp/webapp.network
/etc/containers/systemd/webapp/webapp.pod
----

The same install command, the same application name, the same paths out — one directory over. Quadlet reads `/etc/containers/systemd/` when podman runs as root, exactly as it reads your home directory when it runs as you, and the files land under a directory named after the application both times. The install reloaded the system manager, so the system generator already ran: it read the five files, wrote system units — the same generation, the same wiring, the same `[Install]` applied.

What quadlet deployed — the installed copy, verbatim, the file the generator read:

[source,bash,role=execute]
----
sudo podman quadlet print webapp.pod
----

[source,text]
----
[Pod]
PodName=webapp
Network=webapp.network
PublishPort=8000:8000

[Install]
WantedBy=default.target
----

The `[Install]` section says which systemd target pulls the unit in: `default.target` is the system's boot default — the thing the machine comes up to. Check what systemd recorded:

[source,bash,role=execute]
----
sudo systemctl show -p WantedBy webapp-pod.service
----

[source,text]
----
WantedBy=default.target
----

Note what does not work here: `systemctl enable`. The generated units are written fresh from your declarations at every generation — there is nothing for `enable` to enable. That is not a gap: the generator did enable's job itself, while it was generating. What enable does — link a target to a unit — the generator wrote straight into its output:

[source,bash,role=execute]
----
sudo ls /run/systemd/generator/default.target.wants/
----

[source,text]
----
webapp-pod.service
----

The link `default.target` reads at boot, pointing at `webapp-pod.service` — written by the generator from the `[Install]` section you declared, the same link `enable` would have made. The boot wiring is not a promise; it is on disk.

Start it — one command, no `--user`:

[source,bash,role=execute]
----
sudo systemctl start webapp-pod.service
----

The system manager keeps the unit's log — the same journal command, no `--user`:

[source,bash,role=execute]
----
journalctl --no-pager -u web.service
----

[source,text]
----
Oct 21 08:32:21 rhel systemd[1]: Starting web.service...
Oct 21 08:32:22 rhel systemd[1]: Started web.service.
----

The entries are system entries — the unit is the system manager's, and the filter matches. The store's, the same way:

[source,bash,role=execute]
----
journalctl --no-pager -u store.service
----

[source,text]
----
Oct 21 08:32:21 rhel systemd[1]: Starting store.service...
Oct 21 08:32:22 rhel systemd[1]: Started store.service.
----

The application's own lines are still in podman's log file — the same split as the user side; `sudo podman logs systemd-web` reads them.

Setup pulled the images into root's storage — the same images your user pulled, pre-pulled at provision so the first start has nothing to fetch. Then the application, from root's side:

[source,bash,role=execute]
----
sudo podman quadlet list
----

[source,text]
----
NAME              UNIT NAME               PATH ON DISK                                    STATUS         APPLICATION  POD
store.container   store.service           /etc/containers/systemd/webapp/store.container  active/running webapp       webapp.pod
store.volume      store-volume.service    /etc/containers/systemd/webapp/store.volume     inactive/dead  webapp
web.container     web.service             /etc/containers/systemd/webapp/web.container    active/running webapp       webapp.pod
webapp.network    webapp-network.service  /etc/containers/systemd/webapp/webapp.network   active/exited  webapp
webapp.pod        webapp-pod.service      /etc/containers/systemd/webapp/webapp.pod       active/running webapp
----

The same command that listed your five quadlets, pointed at root's: same names, same application, same table — and a STATUS column that is not `inactive/dead`. Plain `podman quadlet list` still shows your five, stopped; root's install is invisible to it. The pod and both containers are `active/running` under the system's manager; the network holds `active/exited` — it ran, and systemd keeps it recorded; the volume is back to `inactive/dead` — it created the volume and finished. The files are identical; the service is not yours.

Reload http://webcounter-{guid}.{domain}/[*the web counter*^] in your browser: the page renders, and the count starts over at `1` — the named volume is root's too. Your volume held the count; root's starts fresh. Same declarations, different world.

And at boot: the system manager has been running since the machine started. It brings `default.target` up, the generator's link pulls in `webapp-pod.service`, and the application comes up with no session and no one's hands on it. The lab cannot reboot to show it — but every link in the chain is on disk and demonstrated: the files in `/etc/containers/systemd/`, the generator's link beside them, and the `[Install]` section you declared that put it there.

== A Service

You took an application and made it a service — twice. First a user service: five files in your home directory, rootless, wired by a generator, started with `--user`, its data in a named volume of your own. Then a system service: the same five files, one directory over, under the system's manager — nothing in them changed, and the application went from something you run to something the machine runs. That is what a declaration buys: the application is five small text files instead of three commands in someone's shell history, and five small text files run anywhere — under your manager or the system's, on this machine or a hundred. That is where the podman system role picks up.
