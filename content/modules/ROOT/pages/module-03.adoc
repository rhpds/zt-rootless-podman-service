= Systemd Runs It

The application is running as a service: five declarations, one start command, the wiring generated. In this module you will manage it the way services are managed — stop it and start it with systemctl, read its logs, replace a piece without losing its data.

== Stop It, Start It

Stopping is the same operation the hand-run did, with the service's verb:

[source,bash,role=execute]
----
systemctl --user stop webapp-pod.service
----

Check what is left:

[source,bash,role=execute]
----
podman pod ps
----

[source,text]
----
POD ID        NAME        STATUS      CREATED     INFRA ID    # OF CONTAINERS
----

Nothing. The hand-run's `podman pod stop` left an exited pod behind, waiting to be started or removed; the generated unit does not leave the application half-alive. Its `ExecStopPost` runs `podman pod rm --force` — systemd stops the pod and removes it. Stopping a service tears the application down completely.

Starting it builds it back:

[source,bash,role=execute]
----
systemctl --user start webapp-pod.service
----

Reload http://webcounter-{guid}.{domain}/[*the web counter*^] in your browser: the page renders again, and the count kept going — it did not start over.

image::webcounter-service.png[]

The pod was torn down and rebuilt from scratch, and the count survived — because it is not a property of the pod. It lives in the store's named volume, `store-data`, which systemd did not touch: the volume is declared, and stopping services does not remove it.

== The Logs

There is no shell in these images — what the application writes to its logs is the debugging surface. Podman keeps each container's output, and `podman logs` reads it — the container name is the address:

[source,bash,role=execute]
----
podman logs systemd-web
----

[source,text]
----
[2026-10-20 20:27:13 +0000] [2] [INFO] Booting worker with pid: 2
[2026-10-20 20:27:13 +0000] [3] [INFO] Booting worker with pid: 3
store reached at localhost:6379
store reached at localhost:6379
----

The same lines the pod returned — the frontend's gunicorn workers booting, and the store connection on every page load. The container's output is podman's to keep — it goes to the container's log file, not the journal. `podman logs` is the service's log view, and the container name is the address.

The store's log shows the other half — where its data comes from:

[source,bash,role=execute]
----
podman logs systemd-store
----

[source,text]
----
1:M 20 Oct 2026 20:27:13.059 * DB loaded from disk: 0.000 seconds
1:M 20 Oct 2026 20:27:13.059 * Ready to accept connections tcp
----

On every start the store loads its data from disk — the named volume mounted at `/data`. The log does not say which volume; the declaration does.

== Replace a Piece

[WARNING]
====
This prose is terrible — it needs to be framed around an update or change to a single component of a pod.
====

The store's service manages one container. Stop it:

[source,bash,role=execute]
----
systemctl --user stop store.service
----

The application never stopped — the pod is still running, the frontend still serving. Check what is left:

[source,bash,role=execute]
----
podman ps --format "{{.Names}}"
----

[source,text]
----
webapp-infra
systemd-web
----

The store's container is not exited — it is gone. The generated unit's `ExecStop` runs `podman rm -v -f`: stopping the service removes the container. The container is gone. The data is not:

[source,bash,role=execute]
----
podman volume ls
----

[source,text]
----
DRIVER      VOLUME NAME
local       store-data
----

The volume `store-data` — declared in `store.volume`, named — is untouched by the container's removal. Start the service again:

[source,bash,role=execute]
----
systemctl --user start store.service
----

The service regenerates the container from the declaration — no container by that name exists (the stop removed it), so it creates a fresh one. Reload http://webcounter-{guid}.{domain}/[*the web counter*^] in your browser: the count kept going. The container is brand new; the data is not — it lives in the named volume, which every store container mounts and none of them owns.

image::count3-replaced.png[]

Without the declaration, this is the step that would have reset the count to `1`: the image's data point would have landed in an anonymous volume, discarded with the container. Writing it down — `Volume=store.volume:/data` in the declaration — is what moved the count out of the container.

A running service is not yet a service that comes back.
